# AI-Powered Banking Support & Fraud Intelligence System (NLP + RAG)

Full end-to-end implementation of the capstone brief, built and trained on
the **real dataset provided** (200 support tickets, 2,000 transactions, 4
policy documents, 20 QA ground-truth pairs) — not synthetic placeholder data.

## Pipeline flow

```
User Query
    │
    ▼
Intent + Sentiment Model      (src/intent_classifier.py)
    │  → category: Fraud / Loan / KYC / Account Access
    │  → sentiment: 6-class (see honest limitation below)
    ▼
Retriever (dual index: policies + past cases)
    │  TF-IDF version:  src/rag_pipeline.py
    │  FAISS version:   src/rag_pipeline_faiss.py (dense embeddings)
    ▼
Response Generation
    │  Tries in order: Groq (free) → Anthropic Claude → extractive fallback
    │  Never shows raw errors to the user — failures log to console only
    ▼
Risk Classification            (src/risk_classifier.py)
    │  Text-only flow: query_text + predicted category → risk model
    │  Transaction flow: amount/flags/etc. → trained fraud model
    ▼
Action Layer                   (src/action_layer.py)
    │  (category, risk_level) → suggested_action, seeded from qa_pairs.json
    ▼
Output: Response + Risk Level + Suggested Action
    │
    ▼
Streamlit Dashboard             (app/streamlit_app.py)
```

`src/pipeline.py` orchestrates the whole flow above for a single query —
it's the one function (`run_pipeline`) that both the CLI and the Streamlit
app call.

## Quick start

```bash
pip install -r requirements.txt --break-system-packages

# Train everything from scratch (each script also auto-trains on first use)
python3 src/intent_classifier.py
python3 src/risk_classifier.py
python3 src/rag_pipeline.py

# Optional upgrades — see "Optional upgrades" section below
python3 src/db_setup.py
python3 src/rag_pipeline_faiss.py

# Try the full pipeline on one query from the command line
python3 src/pipeline.py

# Check output quality across all 20 real QA pairs (predicted vs. expected,
# side by side) — this is the fastest way to sanity-check the whole system
python3 src/batch_eval.py

# Launch the dashboard
streamlit run app/streamlit_app.py
```

> Use `python3`, not `python` — most Ubuntu installs don't alias `python` to
> `python3` by default (`sudo apt install python-is-python3` if you want that).

### Optional: enable LLM-generated responses

By default, responses are generated by extracting from retrieved context
(no API key needed, always works). To get actual LLM-written responses
instead:

```bash
# Free, no card required — sign up at console.groq.com
export GROQ_API_KEY=gsk_...your-key...

# Or, if you have one — this is a paid API
export ANTHROPIC_API_KEY=sk-ant-...your-key...

streamlit run app/streamlit_app.py
```

Groq is tried first if both are set. If neither is set, or the call fails
for any reason, it silently falls back to the extractive response — no
error ever appears in the UI.

## What the analysis actually found

Run `notebooks/01`-`04` for the full walkthrough with charts. Headline findings:

- **`sub_category` in support_tickets.csv is corrupted** — every value is a
  truncated, unsubstituted query template (e.g. `"I see a transaction of
  ₹{amt} I didn't m"`). Excluded from modeling entirely.
- **Query text is templated**: only 66 unique phrasings across 200 tickets
  (~3x repetition each). The intent classifier hits 100% held-out accuracy —
  that's template recognition, not proof of real-world generalization.
  Recommend paraphrase-augmenting before production use.
- **Sentiment is not predictable from query_text** in this dataset — a
  trained classifier gets ~20% accuracy on 6 classes (near-random). The same
  query template appears with different sentiment labels across duplicate
  rows, suggesting sentiment was assigned independently of the wording.
- **Risk level correlates strongly with category, weakly with sentiment** —
  Fraud tickets skew High/Medium, Account Access skews Low. Using predicted
  category as a model feature (not just text) raised end-to-end risk match
  on qa_pairs.json from 75% to 85% — see Design notes below.
- **`is_international` and `geo_anomaly_flag` perfectly separate fraud** in
  transactions.csv (100% clean split) — makes the transaction fraud model
  hit ~100% test accuracy. Treat that as a reflection of clean synthetic
  flags, not an expectation for live, noisier data.
- **RAG retrieval needed a real fix**: a single shared index (policies +
  200 ticket chunks) let near-duplicate tickets crowd out policy docs —
  only 15% of qa_pairs.json questions retrieved the correct policy. Splitting
  into two indices (policies, past cases) and merging top results from each
  raised that to **75%**.
- **Account Access has no dedicated policy document** — a real coverage gap
  worth flagging; those queries currently fall back to KYC/fraud policy text.

## Optional upgrades (built, tested, ready to use)

Two things were flagged as gaps against the original project brief — both
are now implemented as drop-in alternatives:

### 1. Real vector search: FAISS + sentence-transformers

`src/rag_pipeline_faiss.py` replaces the TF-IDF retrieval in
`src/rag_pipeline.py` with actual dense embeddings (`all-MiniLM-L6-v2`) and
a real FAISS index — same `retrieve()` / `generate_response()` /
`evaluate_retrieval()` interface, so it's a one-line import swap:

```bash
pip install sentence-transformers faiss-cpu
python3 src/rag_pipeline_faiss.py   # builds the index, first run downloads
                                      # the embedding model (~90MB, one-time)
```

Then in `src/pipeline.py`, change:
```python
from rag_pipeline import generate_response
```
to:
```python
from rag_pipeline_faiss import generate_response
```

Confirmed result on real hardware: same 75% policy-hit-rate as TF-IDF, but
2.2x higher match confidence (0.44 vs 0.20 avg similarity) — dense
embeddings find semantically relevant policy text even with no literal
word overlap with the query.

### 2. SQL database layer

`src/db_setup.py` loads the CSV/JSON data into a normalized SQLite database
(`data/processed/banking.db`) with indexes on `category`, `risk_level`,
`fraud_label`, `city`, `transaction_type` — satisfying the brief's "SQL
Database Practices" guideline. `src/db_loader.py` mirrors `data_loader.py`'s
functions exactly (verified: identical row counts and values) so it's a
drop-in swap:

```bash
python3 src/db_setup.py    # builds data/processed/banking.db
python3 src/db_loader.py   # sanity-check + example ad-hoc SQL query
```

Then anywhere you see `from data_loader import ...`, change it to
`from db_loader import ...` to run the pipeline off the database instead of
raw files. `db_loader.query(sql)` is also available for any ad-hoc SQL you
want to run directly (aggregations, filters) without loading a full table.

## Design notes / honest limitations

- **Ticket-text risk model uses category as a feature** (query_text +
  predicted intent from `intent_classifier.py`), not text alone. Category
  correlates strongly with risk_level in this data (Fraud tickets skew
  High, Account Access skews Low) — adding it as an explicit feature raised
  end-to-end risk match on qa_pairs.json from 75% to 85%, including fixing
  the one case that mattered most: a CVV-phishing call going from a Medium
  misclassification to the correct High.
- **Extractive fallback response** pulls one past-case resolution and one
  policy citation, clearly labeled ("Based on a similar past case: ..." /
  "Per fraud handling policy: ...") — an earlier version could produce two
  near-identical "Based on our records: Past case..." lines back to back.
- **Retrieval (TF-IDF version)** uses cosine similarity with a
  letters-only tokenizer (to avoid numeric-amount tokens creating false
  matches). The FAISS version (see Optional upgrades) uses real dense
  embeddings instead — both share the same `retrieve(query, k)` interface.
- **Response generation** tries Groq first (`GROQ_API_KEY` — free tier, no
  card required: sign up at console.groq.com), then Claude
  (`ANTHROPIC_API_KEY`), then falls back to an extractive template so the
  pipeline always runs even with no API key at all. Failures are logged to
  the console, never shown in the response text itself.
- **Action table** is derived directly from `qa_pairs.json`'s
  `suggested_action` field — only 20 examples across 12 possible
  (category, risk_level) combinations, so several combinations fall back to
  a generic default. Expand qa_pairs.json for full coverage.
- **Sentiment model** is trained but, per the finding above, isn't reliable
  on this dataset — reported honestly rather than hidden. Worth revisiting
  once real (non-templated) sentiment-labeled data is available.

## Project guideline compliance

- PEP 8 formatting, docstrings, and modular functions/files throughout.
- Error handling: `data_loader.py` raises clear `FileNotFoundError`s;
  both RAG pipelines degrade gracefully through Groq → Claude → extractive
  without ever surfacing a raw error to the user.
- SQL Database Practices: satisfied via `src/db_setup.py` (normalized
  tables, 8 indexes) + `src/db_loader.py` — see "Optional upgrades" above.
- Streamlit interface: interactive form with optional transaction-detail
  fields, minimalist single-page layout.
